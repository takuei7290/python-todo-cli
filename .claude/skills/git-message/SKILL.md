# git-message

このリポジトリはPython学習用の練習プロジェクト。CLAUDE.mdの方針により、ユーザー自身がgit操作を実行して学ぶことを重視している。このスキルの役目は「文面を考える」ことだけで、実際に `git commit` や `gh pr create` を実行するのはユーザー自身。コマンドを代わりに実行しない。

## 呼ばれたときの分岐

- 「コミットメッセージ」に関する依頼 → [コミットメッセージを考える](#コミットメッセージを考える)
- 「PR」「プルリク」に関する依頼 → [PRメッセージを考える](#prメッセージを考える)
- どちらか曖昧なとき: `git status` の結果を見て、pushしていないコミットが複数あればPR、それ以外はコミットメッセージとして扱ってよいが、迷ったら一言確認する。

## コミットメッセージを考える

1. `git diff --staged` (ステージされていなければ `git diff`) と `git status` で変更内容を確認する。
2. 変更が複数の意図を含む場合(例: 機能追加とリファクタが混在)、無理に1つにまとめず、分けてコミットすべきであることをユーザーに伝える。
3. このリポジトリの過去のコミット(`git log --oneline -10` で確認できる)は次のような日本語のConventional Commits風スタイル:
   - `feat: タスク完了(done)機能を実装`
   - `refactor: タスク読み込み処理をload_tasks()関数に共通化`
   - `docs: ...` (ドキュメントのみの変更)
   - `fix: ...` (バグ修正)
   このスタイル(`<prefix>: <日本語の要約>`)に合わせる。prefixは変更内容に応じて選ぶ(feat/fix/refactor/docs/test/chore)。
4. 要約は「何をしたか」を簡潔に。理由や経緯は本文が必要なほど複雑でなければ書かなくてよい。
5. 出力は以下の形式で、コードブロックにして貼り付けやすくする:

```
<prefix>: <要約>
```

Claudeが書いた/生成したことを示す署名(Co-Authored-Byなど)は付けない。本文(詳細説明)が必要なほど変更が大きい場合のみ、要約の下に空行を挟んで箇条書きの説明を足す。

## PRメッセージを考える

1. 現在のブランチ名と、mainとの差分を確認する: `git log main..HEAD --oneline` と `git diff main...HEAD --stat`。
2. タイトルは短く、コミットメッセージと同じ `<prefix>: <要約>` 形式に合わせる。複数コミットがある場合は一番大きな変更を代表させるか、まとめた要約にする。
3. 本文はこのリポジトリのCLAUDE.mdの運用(feature/docsブランチ → コミット → push → PR → Merge commitでマージ)を踏まえ、次の構成にする:

```
## 概要
<何を変更したか、なぜ変更したかを2〜3行で>

## 変更内容
- <変更点を箇条書きで>

## テスト
- <動作確認した内容。学習用プロジェクトなので `python todo.py ...` を手動実行して確認した、のような簡潔な記述でよい>
```

Claudeが生成したことを示す署名("Generated with Claude Code"など)は付けない。

4. マージ方式は必ずMerge commitであることを前提にする(squashやrebaseの言及はしない)。
5. タイトルと本文をそれぞれコードブロックで分けて提示し、ユーザーが `gh pr create --title "..." --body "..."` にそのまま使えるようにする。

## やらないこと

- `git add` / `git commit` / `git push` / `gh pr create` などの実行はしない。文面を提示するだけ。
- ブランチの作成や削除もこのスキルの範囲外。
